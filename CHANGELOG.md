## [Unreleased]

### Added

- **A secondary (non-login) email or phone is now confirmable too, not just the sign-in one (AUTH-51).** Decision 1 of `docs/adr/005-value-confirmation.md`, superseding the last bullet of ADR 001's decision 2. Unlike the sign-in value, a secondary one is still saved on submit as before — only its proof happens separately, through a new explicit "Confirm" action next to it in `my/` (`POST my/confirm/send/<section>/`, `authFrontendMyConfirmSendController`), which sends a link (email) or a code (phone, reusing `my/confirm/` for the code-entry step) and stamps `status = confirmed` once it comes back. `authProfileSectionEmail`/`Phone` now implement `authProfileSectionConfirmable`; the mailing/texting logic itself is shared with the sign-in twins through three new traits (`authProfileConfirmableValueTrait`, `authProfileConfirmEmailTrait`, `authProfileConfirmPhoneTrait`) instead of being duplicated a second time
- **`login_require_confirmed`** — a new per-domain setting (default off) that blocks sign-in until the login email has been confirmed, via `authLoginConfirmGate`. Off by default so upgrading the app never silently locks anyone out; effective only together with `signup_confirm` and `email` in `signup_fields` (`authLoginConfirmGate::isEnabled()`), and only for `authEmailMethod` — `authPhoneMethod`'s own OTP success is itself the proof, and `authLoginMethod` has no confirmation storage to check at all. See decisions 4–6 of `docs/adr/005-value-confirmation.md`. Backend toggle on the "Login" screen, with a warning when it has no effect yet and when it will lock out unconfirmed existing accounts
- **`confirm/` (no token) — resend of the signup confirmation link**, the recourse the strict-login gate above requires: a contact whose original 24h-TTL link expired, or one that never went through signup confirmation at all (created via OAuth/import), now has a way back in once it needs one. Same anti-enumeration contract as password recovery — the response never reveals whether the address resolved or was already confirmed. `authSignupConfirmModel::deleteByContact()` backs a resend replacing the earlier live token rather than piling up alongside it
- `authContactStatus` — the one place that stamps `wa_contact_emails.status`/`wa_contact_data.status` confirmed, normalizing per field (phone through the same `transformPhone()`+`cleanPhoneNumber()` chain a save uses) so callers never have to know the two models' storage disagree on what "unknown" looks like

### Changed

- **Five sites now stamp `status = confirmed`, none of which did before (AUTH-51):** confirming a login change in the profile (after the value is actually written, not before — writing it first was necessary so `authProfileValues::preparePhones()`'s carry-by-value logic doesn't read the just-written number back as unconfirmed); completing signup confirmation (`authFrontendConfirmAction`, now against the address the link was actually mailed to — `auth_signup_confirm` gained an `email` column — rather than whatever sits at sort 0 when the link is clicked); a successful phone OTP login (`authPhoneMethod::verifyOtp()`); a completed password recovery on either channel (`authFrontendRecoveryAction::finishRecovery()`, via `authRecovery::pendingChannel()` for the code-based path); and the new "Confirm" action for an already-stored secondary value. See decision 7 of `docs/adr/005-value-confirmation.md`
- `auth_profile_confirm` gained a `section` column, closing a handoff hijack found while designing this task: resolving a pending row's section by its `field` alone, at redemption time rather than at issue time, let a row issued by the plain email/phone section redeem through the sign-in section instead (or the reverse) if `login_methods` changed while the row's 1h TTL was still live — promoting a secondary address to the sign-in login without ever checking `isTaken()` on it. `authFrontendMyConfirmAction` now resolves strictly by the issuing section, falling back to the old field-based resolution only for a row issued before this column existed. See decision 2 of `docs/adr/005-value-confirmation.md`
- The "Confirm" endpoint's throttle (`otp_send` scope, shared with `authPhoneMethod`/`authPhoneRecoveryProvider`'s SMS spend) now also covers `authProfileSectionLogin::getConfirmationUrl()`, which previously had no rate limit at all on repeated sign-in-email-change requests — both now go through the same guarded `authProfileConfirmableValueTrait::startConfirmation()`

### Security

- **Password recovery no longer leaks whether an email address or phone number belongs to an account (AUTH-48).** The old single email-only form already avoided this for its one path, but a naive extension to a second, code-based channel (phone) would not have: a form whose success state *is* a code-entry step turns "pending code exists → show it, otherwise → show 'sent'" into an instant, per-number enumeration oracle. `authPhoneRecoveryProvider::start()` now always issues a pending row and always returns the same "enter the code" response, real number or not — the decoy row for an unresolved number carries a real, hashed, never-sent code and fails a guess exactly like a real one, same attempt counter, same TTL, same fate on the fifth wrong try. The paid-resource throttle (`otp_send`) is checked, and refuses, identically for both cases too — real and made-up numbers trip it on the same request count and get the exact same "too many attempts" response (`authRecoveryThrottledException`, caught by `authRecovery::request()`) — so the giveaway can't just move one layer down into how soon repeat requests start being refused. See `docs/adr/004-recovery-channels.md`, decision 5
- **Password recovery matched an email case-sensitively, unlike everywhere else in the app.** `bob@x.com` and `Bob@X.com` were two different lookups on the recovery form even though `authProfileSectionLoginEmail::normalize()` and `authThrottle` both already lowercase the same value — a visitor who signed up with a capital letter and typed their address in lowercase got the "we sent it" screen and no mail. Fixed by `authEmailRecoveryProvider`, which normalizes the same way the rest of the app does
- **A domain signing people in only by `wa_contact.login` (`authLoginMethod`) had no way to recover a lost password at all.** `HAS_RECOVERY` used to be a constant on the login *method*, and `authLoginMethod`'s was `false` — so `recovery/` 404'd on such a domain regardless of `recovery_enabled`, even though the account has a real password to reset. Recovery availability no longer asks any method; it only asks whether *some* enabled method uses a password (`authHelper::hasPasswordLogin()`) and whether at least one recovery channel is configured
- **The new-password step in recovery accepted anything, including an empty or absurdly long password.** `authProfileSectionPassword` already enforced non-empty and `waAuth::PASSWORD_MAX_LENGTH`; the recovery form's own password step (`authFrontendRecoveryAction`) did not. Both now share one rule set, `authHelper::validateNewPassword()`, so the two paths cannot drift apart again
- **Repeated recovery requests for the same address/number used to pile up live tokens instead of replacing the earlier one.** `auth_password_recovery` had no unique key on the request itself; a stale link or code from an earlier attempt (e.g. before a typo was corrected) stayed usable alongside the new one. Now unique on `(identifier_hash, channel)` — see `docs/adr/004-recovery-channels.md`, decision 6, for why that key is the identifier's hash and not `contact_id` (every decoy row shares `contact_id = 0`; keying on it there would let two unrelated decoys collide and swap attempt counters)
- **The sign-in form is now protected against password guessing (AUTH-49).** Until now nothing counted failed attempts anywhere in the app: the login form had no limit at all, and the three ad hoc counters that did exist (`authPhoneMethod`'s OTP send cap/cooldown, `authTotpPlugin`'s 5-guess cap) lived in the session and reset the moment a visitor dropped their cookie. A new core service, `authThrottle`, now runs *before* a login request resolves to a contact — `authGuard` structurally can't do this, since guards only run after `authenticate()` already succeeded (see `docs/adr/003-credential-throttle.md`) — and counts two independent windows per attempt: the typed identifier (email/login/phone, hashed, never stored in the clear) and the source IP from `waRequest::getIp()`. Escalation is a growing refusal window (`throttle_delay` seconds × the attempt count so far) rather than a `sleep()` in the request, and rather than a hard lockout on the identifier: a flat lockout keyed on someone's email is a lever an attacker who merely knows that email would control, not one they'd have to earn, so `throttle_lockout` only ever applies to the IP counter. A real credential mismatch is now its own exception, `authCredentialFailureException extends authGuardException`, thrown only by `authEmailMethod`/`authLoginMethod` on an actual wrong password or unknown login — an empty form submit and `authPhoneMethod`'s own resource limits stay plain `authGuardException` and don't feed this counter. Registration and password recovery count by IP only (a per-identifier limit there would let anyone who knows a victim's email lock them out of recovering their own password, the same lever rejected for login); `authPhoneMethod`'s OTP send cap/cooldown moved out of the session into the same throttle (scope `otp_send`), while the code-guessing cap in `verifyOtp()` stays in the session on purpose — that limit dies with the code it protects. The counter store is the one part of this that's pluggable (`authThrottleStore`, `throttle_store` setting) for installs running more than one app server; everything else — thresholds, windows, delay, lockout, the captcha escalation below — is a fixed set of domain settings, not something a plugin decides
- **Captcha on the sign-in form now has a mode, not just an on/off plugin choice.** `captcha_mode` (`off` / `always` / `after_n`) sits next to `captcha_plugin` on the backend "Brute-force protection" screen (formerly "Captcha") — `after_n` shows it only once a counter above crosses `captcha_after_n` failed attempts, computed from the IP counter alone while the visitor's identifier is still unknown (GET) and from whichever counter is highest once it POSTs. Registration keeps its captcha unconditional at every mode: `after_n`'s escalation needs a sequence of failed attempts to key on, and a signup's first request *is* the thing being defended against, so there is no such sequence to wait for
- **Deleting a named connection of a multi-instance plugin (backend "Login" screen) now unlinks the accounts held under it (AUTH-440).** A connection's account links (`wa_contact_data`, `<source>_id`) and its settings block (`plugin_settings[plugin_id][instance]`) used to have unrelated lifecycles: deleting the connection dropped the settings but left the links behind. Because an instance key is free to reuse (it's validated but never edited in the UI — only retyped via "+ Add connection"), a later connection created with the same key silently inherited a stranger's account: `authContactResolver::find()` matches by the provider's `source_id` alone, with no idea the key had a previous, different provider behind it. Deletion now purges those links in the same save, skipped only when the same connection is still configured on another domain (a link carries no domain dimension, the connection config does — see `docs/adr/002-multi-instance-connection-lifecycle.md`). A plugin with its own per-contact storage beyond the link (a challenge plugin's enrollment secret, say) must override the new `authPlugin::countInstanceContacts()`/`purgeInstanceData()` pair together, or that data would survive the same way links used to

### Removed

- **`HAS_RECOVERY` / `has_recovery` (AUTH-48).** The five built-in login methods' `HAS_RECOVERY` constant, `authHelper::methodHasRecovery()`, and the `has_recovery` key a plugin's `getInfo()` could declare are gone — no plugin in this tree ever declared it. Recovery availability is a domain-level property now (`authHelper::hasPasswordLogin()` + at least one enabled `authRecoveryProvider`), not a flag on whichever method happens to sign someone in; see the `authLoginMethod` fix above and `docs/adr/004-recovery-channels.md`, decision 1

### Added

- **`authRecoveryProvider` — password recovery is now a plugin extension point, the same family as `authMethod`/`authGuard`/`authCaptcha`/`authThrottleStore` (AUTH-48).** Until now recovery was one email-only path hardcoded into `authFrontendRecoveryAction`, with no way for a contact without email (phone-only) to recover at all, and no way for a third-party login method with its own identity model (e.g. a single "email or phone" field) to participate. The core no longer classifies an identifier itself: `authRecovery` tries each enabled provider's `claims()`, in `recovery_channels` order, and the first match owns resolution and delivery end to end. Built-in `authEmailRecoveryProvider`/`authPhoneRecoveryProvider` (registered under ids `email`/`phone`) are ordinary implementations of the same interface, not a special case — a plugin declares `is_recovery_provider` in `plugin.php` and is listed in `recovery_channels` (same id format as `login_methods`) to add its own channel. See `docs/adr/004-recovery-channels.md`
- **Password recovery by phone (SMS code)** — `authPhoneRecoveryProvider`, sharing the `otp_send` throttle scope with `authPhoneMethod` so recovery can't be used to bypass that resend cap
- `recovery_channels` domain setting (default `['email']`) and the "Recovery channels" checklist on the backend "Password recovery" screen
- `authRecoveryHandle` / `authRecoveryResponse` — the plain DTOs `authRecoveryProvider` and `authRecovery` pass between `request()`/`verifyCode()`/`complete()`
- `authRecoveryThrottledException` — the exception a provider's `start()` throws to report its own resource throttle (e.g. `otp_send`) refusing an attempt; `authRecovery::request()` renders it exactly like its own IP-scoped throttle refusal, so a plugin never has to reinvent that message
- `authProfileValues::normalizePhone()` — the phone-normalization chain (`waContactPhoneField::cleanPhoneNumber()` over the domain's `transformPhone()`) already used for profile phones, now public so `authPhoneRecoveryProvider` and the `otp_send` throttle key agree with the rest of the app on what "the same number" means
- `authThrottle`/`authThrottleModel`/`auth_throttle` — the brute-force throttle's service, aggregate-window model and table (AUTH-49); `authThrottleStore` is the interface a counter-store plugin implements, `authThrottleDbStore` the built-in one
- `authCredentialFailureException` — the `authGuardException` subclass a real credential mismatch throws, so the throttle can count it without also counting an empty form submit or `authPhoneMethod`'s own limits
- **The admin sees a linked-account count before deleting a connection**, and confirms — "delete" now marks the block "will be deleted on save" with a "Cancel" link instead of removing it from the page outright, and the server acts only on an explicit `deleted_instances[plugin_id][]` list posted alongside the form, never on a field's mere absence from POST (a truncated request must not read the same as an admin's explicit deletion, now that deletion also purges account links)
- `authContactLinks` — bulk read/delete over `wa_contact_data` for one link source, the admin-side counterpart to `authContactResolver`'s single-contact reads and writes
- `authPlugin::countInstanceContacts()` / `purgeInstanceData()` — the contract a multi-instance plugin's own storage participates in an instance deletion through, documented in README under "Именованные инстансы (multi_instance)"
- `authPluginManager::isValidInstanceKey()` / `filterInstanceBlocks()` — the instance-key validation and deletion-list filtering the backend Login screen and its tests now share one definition of
- `docs/adr/002-multi-instance-connection-lifecycle.md` — the decisions above, plus the same question answered for 2FA enrollment: unlike a link, an enrollment carries no domain dimension while its *enforcement* does, so disabling a challenge plugin (per domain or in `plugins.php`) simply stops asking for the second factor rather than revoking it

### Fixed

- **Deleting the last named instance of a multi-instance plugin didn't stick — it silently reappeared on the next save.** `collectPluginSettings()` skipped a plugin id entirely when POST carried no block for it at all (the case when the last instance's fields simply aren't in the form anymore), so the stored `plugin_settings[plugin_id]` block from before the deletion survived `save()`'s one-level `array_replace()` untouched, and the "deleted" instance came back, unchecked, on the redraw the save produced. The multi-instance branch now always resolves to a result — empty when nothing is left — instead of being skipped

### Added

- **Standalone release tooling** — `compress-app.php` packages the app into `auth.tar.gz` without the Webasyst framework installed, so it can run standalone in CI. It enforces the app's own bundling rules (`plugins/` never ships, `themes/` ships only `default`) plus whatever `lib/config/exclude.php` adds — now including an explicit `plugins/*` entry as a backstop to that built-in rule. `.github/workflows/release.yml` builds and publishes a GitHub Release on every `vX.Y.Z`/`X.Y.Z` tag push: compiles both the app's and the default theme's `.po` catalogs to `.mo`, stamps `css/backend.css`'s first line with the release version, runs `compress-app.php`, and attaches the resulting archive
- **PHPUnit test harness** (AUTH-87) — `tests/`, run with `phpunit` from the app root (see `AGENTS.md`). `authTestTemporaryTablesTrait` shadows an app table with a real `CREATE TEMPORARY TABLE` for the duration of one test so model tests can run against the dev database without touching real rows; `authTestConfigOverrideTrait` substitutes a domain's `authConfig` settings the same way, without writing to `wa-config/apps/auth/config.php`. First slice: `authHelper::localRedirectUrl()`'s open-redirect guard, `authPluginManager::splitInstance()`, the `authConfig` two-level merge, the `login_methods`-driven `authHelper` helpers, and `authProfileConfirmModel`'s TTL/attempt-limit/replace-on-reissue behavior. `lib/config/exclude.php` keeps `tests/` and its runner config out of the release bundle
- **PHP 8.2–8.5 compatibility declared and checked** (AUTH-87) — `lib/config/requirements.php` now states the floor (installer-enforced), both READMEs' "Требования"/"Requirements" sections match. `.github/workflows/php-version-check.yml` lints every file across a PHP 8.2/8.3/8.4/8.5 matrix on push and PR. `psalm82.xml`/`psalm85.xml` pin Psalm to the range's two ends for deeper analysis (deprecations/removals visible only at one boundary), errorLevel 4 like the `sdekint` plugin's own `psalm74.xml`/`psalm85.xml` — but scoping `wa-system`/`wa-config`/`wa-plugins` through `<ignoreFiles>` rather than `<extraFiles>`, so a run reports only this app's own findings instead of also flooding the report with pre-existing framework issues nobody here can fix. `psalm82-baseline.xml`/`psalm85-baseline.xml` freeze the 247 pre-existing findings from the first run, so a plain run now reports clean and only genuinely new issues fail it. See `AGENTS.md` for the local run commands and the level rationale

### Fixed

- `authConfig`'s nullable-by-default parameters (`?string $domain = null` and friends) are now typed explicitly — implicit nullable is deprecated as of PHP 8.4 and was spamming a deprecation notice per call once the new test suite started exercising these methods directly. No behavior change
- The same implicit-nullable fix applied to `authPlugin::getDomainSettings()`, `authProfileFields::getEnabled()`/`isEnabled()`/`filter()`, and `authProfileSectionBase::__construct()`, found by the new PHP 8.2–8.5 compatibility lint. No behavior change

- **The "Link" button in the "Linked accounts" section actually links now (AUTH-50).** Until now it pointed at `$method->getCallbackUrl()`, an ordinary OAuth *login* URL — following it either created a second contact for a visitor whose provider identity was unknown, or silently signed them into whoever's account already held that identity, with no message either way. Clicking it now starts a dedicated round trip: `my/link/<method_id>/` records an `authLinkIntent` for the signed-in contact and sends the visitor to the provider; the same callback route (`auth/callback/<method_id>/`, `oauth.php?app=auth&provider=...`) reads the intent back inside `authContactResolver::resolve()` and calls the new `authContactResolver::link()` instead of find-or-create. Linking never creates a contact and never changes who is signed in — a conflict (the identity already belongs to another contact) throws `authLinkException` with a plain "already linked to another profile" message instead of silently reassigning the row the way the framework's own `waOAuthController::afterAuth()` does; linking an identity already on the visitor's own contact is idempotent. `link_url` in the section's rows keeps its name and stays a plain `<a href>` — themes that copied the partials need no changes. A successful link is logged the same way an unlink already is — `my_profile_edit` with `{"section": "linked_accounts"}` — so the two remain one history; re-linking an identity already on the visitor's own contact is a no-op and logs nothing, matching how unlinking only logs on an actual write
- **Theme `default` has its own locale catalog** (`themes/default/locale/`, domain `auth_themes_default`), generated with `php wa.php locale auth/themes/default`. All 82 `_w()` calls in the theme's `my.profile.*`/`my.confirm.html` templates are now `_wp()`, resolved against the theme's own catalog first. This replaces the workaround from 0.1.0, where theme strings had to be hand-copied into `auth.po` because the app-level generator only keeps already-saved theme entries and never discovers new ones — a theme string is now extracted and translated the same way an app or plugin string is, without touching `auth.po` at all. The 30 msgids that existed in `auth.po` only for the theme's sake have been removed from it accordingly; the handful also used by `lib/` stay
- **Plugin sections in the profile page (`my/`)** — a plugin adds a block to the profile by implementing `authProfileSectionProvider`, the same `authProfileSection` contract core sections use, registered under the domain's own config id for that plugin (never one the plugin picks itself), per decision 7 of ADR 001. No new interface, no new write route: `POST my/save/<section>/` serves plugin sections exactly as it serves core ones. `authPluginManager::getProfileSectionPlugins()` discovers them the same way `is_guard`/`is_challenge`/`is_captcha` are discovered — a `has_profile_section` flag in `plugin.php`, checked against the domain's own enabled-plugin lists. `authProfileSectionPlugin` is the base class plugin sections extend, handling the id and the partial fallback (active theme, then the plugin's own `templates/`) a core section doesn't need
- **`totp` plugin: two-factor enrollment screen** — "Two-factor authentication" block in `my/` (connect / confirm with a code / disable), the first consumer of plugin profile sections. No QR image — an `otpauth://` link plus the base32 secret for manual entry, since no QR encoder is vendored into the framework or the plugin
- **The rest of the profile sections** — photo, email, phone, address, password and account deletion, alongside the name and linked-accounts sections that came before them. The `my/` page is now assembled entirely from sections, each saved on its own
- **Changing a login is confirmed before it takes effect.** An email or a phone that a domain signs people in with is no longer stored on submit: the new value waits in `auth_profile_confirm` while a link goes to the new address or a code to the new number, and the old login keeps working until the visitor answers on the new one. Proof is always delivered to the new value — a message to the address already on file proves nothing about the one being moved to, and a typo would become the login. `my/confirm/` is the page that waits; `my/confirm/<token>/` is the link. A value already used by another account is refused before anything is sent
- **`login_email` and `login_phone` sections** — an email or phone that is an active login method is served by its own section class rather than by the contact-field one with a flag, per decision 2 of ADR 001. Each pair is mutually exclusive by availability, so a field never appears twice, and the credential half sits under "Sign-in and security" and never consults the site's `personal_fields`
- **Multi-value sections** — emails, phones and addresses are edited one value at a time, addressed by the contract's `index`. A value's inputs are rendered by the contact field itself, so a value edited alone posts under the name it would have had inside the whole-list form, and the section merges it back into the stored list before anything is written. Types (work, home, shipping) are editable, which the framework's own rendering leaves as a hidden field
- **`delete_account` section**, off by default and turned on per domain in the new backend **Profile** settings screen. The account is removed through the framework's own `waContact::delete()`, so every app clears what it stored about the person, and the deletion is the only thing behind one overridable method — a later policy (a grace period, a queue) replaces that method and inherits every guard above it
- `authProfileSection::getRedirectAfterSave()` — a save can end the page it was made on. Deleting the account is the case: redrawing the section afterwards would render it from a record that no longer exists
- **Section editing on the profile page without reloading it** — the `my/` page is now assembled from its sections' partials, and each section can be opened, saved and cancelled on its own. Every control is an ordinary link or form first: `my/?section=<id>&mode=view|edit` is a real page with that section opened, and the section form is a real POST answered with a redirect. The theme's `my.profile.js` intercepts both, asks the same addresses over fetch and puts the section the server sends back in place of the old one — so the markup a script leaves on the page is the markup a reload produces, with nothing rendered a second time in JS. Fetched with `X-Requested-With`, that same address answers with the section partial alone
- **Profile page behavior lives in the theme.** The app answers with markup and never decides where it goes: `my.profile.js` is a theme file, and a theme that wants a drawer, an accordion or a field that turns into an input on click edits it instead of hooking into the app. What the app guarantees is the interface behind it — the two addresses above, the response envelope, and the template variables every section partial gets in both modes — documented in README under «Тема дизайна» so that changing the behavior takes no reading of app code
- **Per-section profile save endpoint** — `POST my/save/<section>/` writes one section of the `my/` page and answers with that section's rendered partial: view mode when the save went through, edit mode with the submitted values and the errors when it did not. Saving one section no longer touches the fields of the others, and a partial submit no longer fails validation on required fields it never carried. Without JS the same endpoint is an ordinary post/redirect/get, and a failed save is restored on the page it redirects to
- **`authProfileSectionConfirmable`** — a section whose new value must be proven before it replaces the old one (an email or phone that is a login method, the password) answers the save endpoint with the URL of its confirmation flow instead of being stored, per decision 2 of ADR 001
- **Profile section contract** (`authProfileSection`) and section registry — the `my/` page is described as a list of independently editable sections, each owning the condition of its own existence and telling "unavailable" from "available but empty"; the action hands the theme a ready-made list grouped for rendering, and a group with no available sections disappears on its own
- **`login` auth method** — login/password against the `wa_contact.login` field
- **Dynamic system OAuth adapters** — every framework-level adapter (VK, Google, Facebook, etc.) is now offered in settings automatically, with per-domain credential fields, instead of only Webasyst ID
- License files (Webasyst EULA) and contribution guidelines (`AGENTS.md`)
- Architecture decision records in `docs/adr/`, starting with the config boundaries of the user profile page (`my/`)
- **Two-factor authentication settings** — `challenge_methods` (2FA plugins) can now be enabled per domain from the backend settings screen instead of hand-editing `config.php`
- **Captcha widget** wired into the login and registration forms, with per-domain settings (site key/secret, etc.) for captcha plugins on the backend settings screen
- Clean backend routing — `/settings/` and `/plugins/` replace the old `?module=backend&action=...` query URLs
- Last-visited domain remembered in an `auth_app_domain` cookie, so the bare app entry point returns to it instead of always defaulting to the first domain
- **Backend Plugins page** rebuilt on the standard Webasyst `waPluginsActions` screen: installed plugins get a real settings UI (`waPlugin::getSettings()`/`saveSettings()`) instead of a static read-only list

### Changed

- **Unlinking an account now counts phone OTP as a way back in.** ADR 001 had left it out on purpose while the phone section did not exist and the answer would have been a guess; with that section written, "does this contact have a number the domain signs people in with" has an exact answer, and a lock that refuses a legitimate unlink is not a safer lock. The password is still counted when unlinking and still not counted when removing a login value — removing the email a password is checked against takes the password with it
- Contact-field sections gained two shaping hooks around validation, `prepareData()` and `prepareForStorage()`, mirroring the order the framework itself uses: phone numbers are normalized before they are validated, addresses reshaped after. Multi-value sections merge the submitted value into the stored list in the first of them
- **A value's type survives a save that renumbers the list.** The framework recovers an address type by looking up the same position in the contact afterwards, which holds only while positions do not move — removing the first of three values would file the other two under their neighbours' types. The type is now attached while the answer is still known
- **`my.profile.html` no longer asks the contact form what to show.** The theme walks the groups and sections the action hands it and renders their `html`; it holds no field checks of its own. Visibility comes from three unrelated config sources, and a template answering those questions for itself drifts apart from the app the moment any of them changes — see ADR 001. Sections get their own addresses (`$save_url`, `$edit_url`, `$view_url`) as template variables rather than composing them in Smarty
- `authProfileSection` gained `restoreFailedSave()`: without JS a failed save answers with a redirect, and the request that draws the profile page afterwards has neither the submitted values nor the errors. Sections built out of contact fields put both back into their form; a section without a form inherits a default that restores the errors alone
- **Backend settings screen split into per-domain sections** — Authorization, Registration, Password recovery, Captcha, Protection, Two-factor authentication each get their own screen and URL (`settings/<domain>/<section>/`) instead of one long form; sidebar now shows a domain switcher on top and a static per-domain section list below it
- **Backend settings save via ajax** — saving a section swaps the response in place (with a "Saved" indicator) instead of a full-page redirect with `?saved=1`, matching the sidebar's existing ajax navigation
- Backend settings save now **merges into the domain's stored config** instead of overwriting it wholesale, so saving one section (e.g. Registration) can no longer clobber another section's settings — `plugin_settings` in particular is merged per plugin id, since Login/Captcha/Guards/Challenges all write into it
- **WAID login** now goes through the auth app's own login pipeline instead of the framework's default redirect
- Built-in form methods (`email`, `login`, `phone`) are now derived from the method classes themselves rather than a separate, duplicated label list
- Login form templates decoupled per method, with a `<method>.login_form.html` partial for each
- The JSON response terminator shared by the login and registration controllers is now a single `authJsonResponseTrait` instead of two copies
- `login.html` template variables are assembled once in `authHelper::loginViewData()`, used by both the login form action and the OAuth callback error path
- Backend settings form UI restructured with semantic field/value markup, `wa-checkbox`-styled checkboxes and `wa-select`-wrapped selects

### Removed

- **`authContactForm`** — the class existed to serve one whole-page profile form: `hasField()` let a template ask whether a field was there, `hasOheOfNameFields()` did the same for the three name fields, and `htmlAllExcept()` rendered everything the theme had not laid out by hand. With `my/` assembled from sections none of it has a caller — a section knows its own fields, and the theme gets a ready-made list of sections from the action and asks nothing. What was left, `fromForm()`, only copied a `waContactForm` into a subclass that no longer added anything to it, so the class went with the methods. A theme that still calls any of the three has kept a copy of the app's field logic and belongs on the section list instead

### Fixed

- **Login, registration, password recovery and the 2FA fallback form were hardcoded in Russian** — `challenge.html`, `login.html`, `login.login_form.html`, `email.login_form.html`, `register.html`, `register.confirm.html` and `recovery.html` had no `_w()`/`_wp()` at all, unlike the `my/` templates. Switching a domain's locale to `en_US` left the entire sign-in flow in Russian. Now wrapped in `_wp()`, translated in the new theme catalog above; the email field keeps its original wording ("Email" in both locales, not "Электронная почта") under the msgid `E-mail` rather than `Email`, because `_wp()` treats a translation identical to its own msgid as untranslated and falls through past the theme's catalog to the app's, then the system's — which does carry a `Email` → `Электронная почта` entry and would otherwise have silently changed the field's label
- **A profile section rendered by the JSON save endpoint (`my/save/<section>/`) could resolve a `_wp()` string differently than the same partial rendered by the page.** `authFrontendMySaveController` calls `authProfileSection::render()` directly, without ever going through `setThemeTemplate()`, so the theme's locale domain was never pushed on that path — a colliding msgid (theme vs. plugin) could translate one way on page load and another way in the save response for the same section. `authProfileSectionBase::render()` now pushes the active theme's locale domain(s) itself when none are already active, mirroring what `waView::setThemeTemplate()` does for an ordinary page
- **`totp` plugin: the code used to confirm 2FA enrollment could be replayed at the next login.** `authTotpProfileSection::confirm()` discarded the counter step `verifyCode()` matched, and `saveSecret()` always started `totp_last_step` at `0` — so the just-used confirmation code was still inside the login challenge's ±1-period window. `saveSecret()` now takes the matched step and stores it as the starting `totp_last_step`
- **Plugin-contributed strings (the `totp` enrollment section in `my/`, its login challenge form) never resolved through the plugin's own locale catalog.** `authPluginManager` instantiates plugins directly rather than through `waSystem::getPlugin()`, so neither the catalog load nor the active-plugin push that make `_wp()` work ever ran — `plugins/*/locale/*.po` existed but nothing loaded them, and translated text silently fell back to the app's own catalog (or English, where the app's happened not to carry the same string). `authPluginManager::readPluginInfo()` now loads a plugin's `locale/` the same way the framework does; a new `authPluginManager::withPluginLocale()` activates it (with `popActivePlugin()` in `finally`, unlike `getPlugin($id, true)`) around every point a plugin's own `_wp()` calls run — its profile section's `render()`/`save()` and a challenge plugin's `getFormHtml()`
- **A plugin's `name`/`title`/`description` from `plugin.php`, its `img`, and its `build` were lost for every auth plugin** — `authPluginManager` builds `$info` itself instead of going through `waSystem::getPlugin()`, and never redid the enrichment that call does to `$plugin_info`. Backend screens (Login, Guards, Two-factor authentication, Captcha) and the login page showed the plugin's raw, untranslated `plugin.php` strings; `img`/`build` were simply absent from `getInfo()`. `authPluginManager::readPluginInfo()` now runs the same steps `getPlugin()` does — web path for `img`, `build` from `lib/config/build.php` (or `time()`/`0`), and `name`/`title`/`description` through `_wd('auth_<plugin_id>', …)` against the plugin's own locale catalog
- Challenge (2FA) login screen's "Incorrect code." error was hardcoded in Russian in `authFrontendChallengeAction`, unlocalized like the rest of the app before this release — now `_w()`
- **Challenge (2FA) step showed «Ошибка соединения» instead of logging in, even on a correct code.** `authFrontendChallengeAction` never checked `waRequest::isXMLHttpRequest()`, so it kept answering `js/auth.js`'s `fetch()` requests with a redirect or a re-rendered HTML page instead of the JSON envelope the script expects; `response.json()` failed to parse either, and the resulting error hid a login that had, in fact, already succeeded server-side. Brought in line with `authLoginController`'s XHR handling — success, wrong code and an expired/missing pending session now all answer XHR with `{status: 'ok'|'error', ...}`; post/redirect/get for non-JS clients is unchanged
- Bare backend entry (`webasyst/auth/` with no domain in the path) redirected to the frontend `my/` page instead of the backend dashboard — `routing.backend.php` and `routing.php` both used the literal `''` array key for their own root rule, and `waAppConfig::getRoutingRules()` always merges `routing.php` on top of `routing.backend.php` in the backend environment, so the frontend rule silently won. `routing.backend.php`'s root rule is now `'/?'` — same effective pattern, no longer a colliding key
- Backend settings page lost its layout after the post-save redirect
- Signup guards are now checked before a contact is created, not after
- Registration link hidden on the login page when signup is disabled
- OAuth logins now respect `signup_enabled`; signup UI hidden when only OAuth methods are active
- OAuth/challenge login no longer redirects to a blank page when `redirect_after_login` is unset
- Logout no longer emits an empty redirect when `redirect_after_logout` is stored as `null`; falls back to `/`
- OAuth `afterAuth()` returns explicitly after a blocked signup/login guard instead of reading possibly-uninitialized variables
- Registration rejects an email that already belongs to a user account instead of silently creating a second account that could never log in by email
- `authPluginManager::getSystemAdapters()` guards the adapters directory with `is_dir()` instead of silencing `scandir()` with `@`
- Registration now stops immediately on a failed captcha check, matching login — a guard error could otherwise silently overwrite the captcha error before it reached the user
- Backend Plugins page never got the app header/sidebar (missing `setLayout()`), fixed by replacing the whole screen with the standard plugin page above
- Frontend app root (`/auth/`) 404'd with "Empty module and/or action" — also broke the Design section's theme preview link, which points at this same URL. Now redirects to `my/` (logged in) or `login/` (guest)
- `my/` accepted a `POST` and wrote the contact through `waMyProfileAction::saveFromPost()` — a second, live write path bypassing every rule that `my/save/<section>/` enforces (login-change confirmation, current-password check, sections' `prepareData()`/`prepareForStorage()`, save logging). `authFrontendMyAction` no longer extends `waMyProfileAction`; `POST my/` now answers `405`, and it no longer assembles a whole-page `waContactForm` on every view or hands the theme `form`/`user_info`/`contact`, none of which it read
- `themes/default/theme.xml` only declared 4 of the 21 files behind the `my/` profile page (the `name` and `linked_accounts` partials from an earlier stage). The 17 partials added since — `photo`, `email`, `phone`, `address`, `login_email`, `login_phone`, `password`, `delete_account` (view/edit each) and `my.confirm.html` — were invisible in the design editor's file list even though they worked on disk, so a theme couldn't override one of them the way ADR 001 §6 promises
- The app had no `locale/` catalog, so every string wrapped in `_w()` fell back to its English source regardless of the visitor's locale — most visibly on `my/`, where the profile sections' own text stayed English next to framework-translated field labels. Added `locale/ru_RU/LC_MESSAGES/auth.po` covering the strings `php wa.php locale auth` finds in `lib/`, `templates/` and `api/`, plus the strings only the theme carries — `_w()` in `themes/default/*.html` resolves against the app's own domain, but the app-level generator only scans theme files to keep already-saved entries, not to discover new ones, so those had to be pulled in and translated by hand

### Security

- **Phone OTP hardening** — resends are throttled (60s cooldown, max 5 per flow) so the SMS channel can't be spammed, verification is capped at 5 attempts so a 6-digit code can't be brute-forced within its lifetime, and the code is stored hashed in the session instead of in plain text
- Email confirmation tokens are now issued and validated through `authSignupConfirmModel`, which sweeps expired rows on each new token — expired `auth_signup_confirm` rows no longer linger in the database

- Post-authentication redirects are now confined to the current site. Both the user-supplied `goal_url` and the admin-configured `redirect_after_login` / `redirect_after_register` values pass through `authHelper::localRedirectUrl()`, closing an open-redirect / phishing vector (`//evil.com`, `/\evil.com`, absolute off-site URLs, `javascript:`, CR/LF injection)
- Password-recovery tokens moved out of `wa_app_settings` into a dedicated, self-expiring `auth_password_recovery` table; expired tokens are swept automatically so single-use secrets no longer accumulate indefinitely
- OAuth identities are no longer auto-linked to an existing password account by a bare email match, which allowed account takeover via a provider that doesn't verify emails. Linking now requires either an adapter that vouches for the address (`email_verified` in the payload — set by the Webasyst ID adapter) or the new opt-in `oauth_link_by_email` setting; matching by the provider's own `source_id` is unaffected
- **Webasyst ID callbacks (`auth/callback/waid/`) accepted a request with no `state` parameter at all** — `waWebasystIDAuthAdapter::verifyState()` returns `true` when `state` is simply absent from the request, so a crafted callback URL carrying an attacker-controlled `code` could be handed to a victim to sign them in as the attacker (and, since AUTH-50, to weld the attacker's provider identity onto whichever account the victim was signed into). `authWaidAdapter::verifyState()` now requires a `state` that matches the one generated for this exact request, unconditionally
- **The "Link" round trip requires its own CSRF token.** `my/link/<method_id>/` is a GET (it has to be, to stay a plain navigation to the provider — see AUTH-50 above), so the framework's own CSRF check, which only runs on POST, doesn't cover it. The action now requires a `_csrf` query parameter matching the visitor's `_csrf` cookie before it records a link intent or redirects anywhere, closing the account-takeover path a forgeable link start would otherwise open in combination with the `state` issue above
