# ADR 003. Защита от подбора учётных данных: встроенный throttle, а не guard-плагин

- **Статус:** принято
- **Дата:** 2026-09-15
- **Контекст задачи:** AUTH-49

## Контекст

В ядре `waAuth` штатной блокировки по числу неудачных попыток нет. В приложении на
момент решения защита существует тремя несвязанными кусками: `authPhoneMethod`
(`RESEND_COOLDOWN_SECONDS`/`MAX_SENDS`/`MAX_ATTEMPTS`), `authTotpPlugin`
(`MAX_ATTEMPTS = 5`) — оба в сессионном хранилище с захардкоженными константами — и
капча, включаемая на домен целиком. Форма логина не защищена ничем.

Естественная первая мысль — «это же guard, у нас для этого есть точка расширения».
Она неверна, и этот ADR существует в первую очередь чтобы её не пришлось опровергать
второй раз.

## 1. Существующий `authGuard` структурно не может считать неудачные попытки

**Наблюдение, а не решение.** `authLogin.controller.php` вызывает login-guard'ы
**после** того, как `$method->authenticate()` вернул `$contact_id`. Неверный пароль —
это `authGuardException` из `authEmailMethod`/`authLoginMethod`, перехватываемый выше
по тому же методу с немедленным `return`; до цикла по `getGuardsEnabled('login')`
управление не доходит никогда. Плюс сигнатура `checkLogin(int $contact_id)` не несёт
ни IP, ни введённого логина — попытку против несуществующего контакта не на что
повесить в принципе.

`authGuard` отвечает на вопрос «этому уже опознанному контакту можно входить?».
Throttle отвечает на вопрос «этот ещё не опознанный запрос вообще стоит обрабатывать?».
Это разные точки в потоке, и вторая существующей точкой расширения не покрыта.

**Следствие для реализации.** Метод в `authGuard` не добавляется: интерфейс уже
реализуют `blackmailguard` и `testguard`, дефолтов у интерфейсов в PHP нет — это
ломающее изменение для стороннего плагина. Если по ходу работы понадобится плагинная
точка на неудачу, это отдельный интерфейс со своим `is_*`-флагом: `loadPlugin()` уже
умеет сверять флаг с интерфейсом, `readPluginInfo()` уже читает произвольные флаги.

**Второе следствие: `authGuardException` не является сигналом неудачной попытки.**
Сегодня этим одним классом кидаются три разные вещи: несовпадение учётных данных,
ошибка заполнения формы («Введите email и пароль» — попытки входа не было вовсе) и
срабатывание собственных лимитов `authPhoneMethod`. Счётчик, повешенный на
`catch (authGuardException)`, накручивался бы пустым сабмитом и накручивался бы поверх
уже сработавшего телефонного лимита. Поэтому вводится
`authCredentialFailureException extends authGuardException` — наследование сохраняет
поведение всех существующих `catch` — и кидается **только** при реальном несовпадении
учётных данных. Считается именно он.

## 2. Throttle встроен и включён по умолчанию; плагином оформляется не политика

**Решение.** Ограничение попыток — часть приложения, а не плагин. Приложение
авторизации, не защищённое из коробки, пока админ не найдёт и не включит плагин, —
сломано; `guard_plugins` по умолчанию пуст, и именно так оно бы и стояло.

**Что при этом всё-таки расширяемо.** Граница проходит не между «встроено» и
«плагин», а между политикой и инфраструктурой:

- *Политика* — число попыток, окно, задержка, длительность блокировки, порог эскалации
  до капчи. Нестандартной не бывает; фиксированный набор опций в доменных настройках
  закрывает её целиком. Плагинизировать её — решать задачу, которой нет.
- *Хранилище счётчиков* — нестандартным бывает регулярно: несколько app-серверов,
  общий Redis/memcached вместо MySQL. Отсюда узкий интерфейс стора.
- *Внешняя реакция* — fail2ban, Cloudflare, корпоративный WAF, SIEM. Отсюда событие
  при срабатывании (`wa()->event()`), а не попытка научить приложение всем этим
  интеграциям.

## 3. Два независимых счётчика: по идентификатору и по IP

**Решение.** Считать раздельно по введённому идентификатору — **как он введён, до
резолва в контакт** — и по IP. Не связка `(ip, login)`.

**Почему.** Счётчик по идентификатору закрывает подбор пароля конкретному человеку;
счётчик по IP закрывает credential stuffing и password spraying, где на каждый логин
приходится одна-две попытки и первый счётчик не срабатывает никогда. Только IP —
ломается за NAT и мобильным оператором; только идентификатор — spraying проходит
насквозь. Связка не даёт ни того, ни другого: у неё те же слепые зоны, что у обоих по
отдельности.

**IP берётся из `waRequest::getIp()`.** Он уже разбирает `X-Forwarded-For` только для
доверенных прокси. Собственный разбор заголовка означал бы счётчик, обнуляемый
подстановкой заголовка, то есть отсутствие счётчика.

## 4. Эскалация, а не блокировка: жёсткий lockout — это DoS против известного логина

**Решение.** По умолчанию: задержка → принудительная капча. Жёсткая блокировка входа
для идентификатора — только на заведомо высоком пороге или явным включением админом.

**Почему.** Блокировка по идентификатору управляется атакующим: кто знает чужой email,
тот по своему усмотрению выключает владельцу вход, не зная пароля. Капча и задержка
удорожают перебор, не давая третьей стороне такого рычага. Счётчик по IP, наоборот,
блокировать можно жёстче — там цену ошибки несёт сам источник трафика.

## 5. Капче нужен режим, а не только id плагина

**Решение.** К `captcha_plugin` добавляется настройка режима: `off` / `always` /
`after_n`.

**Почему.** Сегодня капча безусловна во всех точках — проверка в
`authLogin.controller.php`, вторая проверка в `authFrontendRegister.action.php` и общий
рендер в `authHelper::getCaptchaWidget()` (его зовут оба шаблона, `login.html` и
`register.html`). «Капча после N попыток» означает, что они становятся зависимыми от
состояния throttle, и этого нельзя выразить наличием или отсутствием id плагина: плагин
настроен всегда, вопрос в том, когда он показывается. Это и есть то пересечение с
`captcha_plugin`, которое отмечено в постановке AUTH-49.

**Регистрация — исключение: там капча остаётся безусловной при любом режиме.**
`after_n` опирается на последовательность неудачных попыток, от которой можно
эскалировать; у регистрации такой последовательности нет — первый же успешный запрос и
есть то, что атакующий хотел. Режим — свойство защиты входа, а не домена целиком;
капча на регистрации выключается снятием самого `captcha_plugin`.

## 6. Сообщения throttle не восстанавливают утечку перечисления

**Решение.** Текст, показываемый при срабатывании, не различает «такого пользователя
нет» и «пароль неверный».

**Почему.** `authEmailMethod`/`authLoginMethod` намеренно дают один и тот же текст для
обоих случаев. Сообщение вида «слишком много попыток входа в этот аккаунт», приходящее
только для существующих логинов, возвращает ровно ту утечку, которую они закрывают, —
причём в более удобной для атакующего форме: оракул, отвечающий пакетно.

## 7. Сессия — неподходящее хранилище для счётчиков подбора

**Решение.** Счётчики throttle живут вне сессии. Существующие сессионные счётчики
разделяются по признаку «что именно ограничивается»:

- *Лимит попыток ввода одноразового кода* (`authPhoneMethod::verifyOtp()`) **остаётся в
  сессии**: он привязан к жизни одного конкретного кода, вместе с которым и исчезает.
  Сброс сессии здесь обесценивает и сам код — обхода нет.
- *Лимит отправок SMS* (`MAX_SENDS`, `RESEND_COOLDOWN_SECONDS`) **переезжает в общий
  throttle**: это расход платного ресурса, релевантный IP, и сейчас он обходится
  сбросом куки.
- *Лимит попыток 2FA-кода* (`authTotpPlugin`, 5 попыток в сессии) обходится тем же
  сбросом куки, но код при этом, в отличие от OTP, остаётся валидным — TOTP не привязан
  к сессии. Шестизначный код при снятом лимите перебираем, поэтому счётчик должен быть
  привязан к контакту, а не к сессии.

## 8. Хранилище — своя таблица; `wa_login_log` не подходит

**Решение.** Собственная таблица агрегатных строк вида
`(key_hash, key_type, scope, window_start, last_attempt, count)` — не строка на попытку.
Чистка ленивая, на записи. Идентификатор хранится хешем. `last_attempt` нужен не для
самого лимита, а для нарастающей задержки и `retry_after`: одного счётчика в окне для
них не хватает.

**Почему не `wa_login_log`.** У неё `contact_id NOT NULL`, и пишутся туда только
успешные сессии (`datetime_in`/`datetime_out`, из `waAuthUser` и `waUser`). Неудачная
попытка по несуществующему логину в эту схему не ложится вовсе. Ничего другого в ядре
нет — проверено.

**Почему агрегат, а не журнал попыток.** Журнал — это неограниченно растущая таблица,
которую кто-то должен чистить по расписанию, и повод для отдельного разговора о том,
что в ней хранятся введённые пользователями строки. Агрегатные окна дают тот же ответ
на единственный задаваемый вопрос («сколько за последнее окно») при постоянном размере.
Хеш идентификатора — потому что в сыром виде это email.

## Охват

| Точка | Считать | Почему |
|---|---|---|
| POST формы логина | да | основная цель |
| Регистрация (`authFrontendRegisterAction`) | да, только по IP | неаутентифицированный POST, создающий контакты и рассылающий подтверждения; счётчика по идентификатору нет — он в каждой попытке новый |
| Восстановление пароля (`authFrontendRecoveryAction`) | да | абьюз рассылки писем; канальная специфика — за AUTH-48 |
| Отправка OTP (`authPhoneMethod::sendOtp()`) | да | расход платного ресурса, п. 7 |
| Ввод кода 2FA (`authTotpPlugin`) | да, по контакту | шестизначный код, п. 7 |
| Ввод OTP (`authPhoneMethod::verifyOtp()`) | нет, остаётся в сессии | ограничение живёт не дольше кода, п. 7 |
| OAuth-вход (`authOAuth`, `authFrontendCallback`) | нет | подбор происходит у провайдера, он его и лимитирует |

## Приложение: отклонения, обнаруженные при реализации

Ниже — расхождения между текстом задачи AUTH-49 (см. описание тикета) и тем, что
реально реализовано. Решения выше по файлу не пересматриваются.

**Миграция всё-таки нужна.** Постановка задачи предполагала правку `db.php` без
файла в `lib/updates/`, на основании «продакшен-установок не существует». Это
неверно даже локально: `lib/config/db.php` применяется целиком только при первом
запуске приложения (`waAppConfig::install()`), а эта dev-установка уже прошла
install на версии 0.2.0 — без `lib/updates/1789430400.php` таблица `auth_throttle`
не появилась бы вообще. Файл — точная копия прецедента `1785110400.php`.

**`throttle_delay` — окно отказа, а не `sleep()`.** Растущая задержка реализована
отказом принимать попытку до `last_attempt + attempts × throttle_delay` секунд, с
возвратом `retry_after`, а не как задержка внутри обработчика: `sleep()` в PHP-FPM
держит воркер и лок сессии на всё время сна, то есть исчерпать пул воркеров дешевле,
чем подбирать пароль.

**Колонка называется `attempts`, не `count`.** `COUNT` — зарезервированное имя
функции MySQL, а модель формирует SQL вручную (`ON DUPLICATE KEY UPDATE`); имя
заодно совпадает с уже существующей колонкой `auth_profile_confirm.attempts`.

**Домена в ключе нет.** IP и контакт — общеустановочные сущности, не привязанные к
конкретному домену; пороги при этом читаются из конфига того домена, на который
пришёл запрос. Общий счётчик на несколько доменов одного инсталла ошибается в
строгую сторону.

**Окно — фиксированный бакет, не скользящее.** `window_start = ⌊t / window⌋ × window`
вместо чтения-и-решения по предыдущей попытке: одновременные попадания в один и тот
же бакет складываются атомарным `INSERT … ON DUPLICATE KEY UPDATE` без отдельной
блокировки. Плата — burst на границе окна (до 2× лимита), тот же trade-off, который
задача имела в виду словом «агрегатные окна».

**Восстановление пароля считается только по IP, без капчи.** Задача перечисляла эту
точку без уточнения ключа. Счётчик по email здесь означал бы тот же управляемый
атакующим рычаг, что решение 4 отклоняет для входа — знание чужого адреса давало бы
возможность заблокировать владельцу восстановление пароля. Капча на восстановление
не добавлена вовсе: `recovery.html` сегодня не получает `captcha_widget`, и это
отдельное решение, не часть AUTH-49.

**`authTotpPlugin` (2FA) не тронут в этом проходе.** Плагин живёт в отдельном
git-репозитории (`plugins/totp/`) с собственным циклом релиза; перевод его
сессионного счётчика на throttle-по-контакту (решение 7 выше) требует уже
выпущенного `authThrottle` как зависимости и пойдёт отдельной задачей.

**`otp_send` пересаживается на throttle с другим шагом задержки, не с тем же, что у
пароля.** Старые `RESEND_COOLDOWN_SECONDS = 60` / `MAX_SENDS = 5` действовали только
внутри жизни одного кода: `if ($active)` проверял их лишь пока для этого телефона ещё
не истёк текущий OTP (TTL 300 секунд), а после истечения ни cooldown, ни счётчик
отправок не применялись вовсе — то есть старая защита была «60 секунд между отправками
и обрыв на пятой в рамках одного кода, без ограничения между кодами». Новая — растущая
задержка в 900-секундном окне, независимо от жизни конкретного кода, и в этом смысле
строго сильнее заменяемой. Общий `throttle_delay`
(секунды, растущие от количества попыток) настроен под подбор пароля и по умолчанию
равен 2 — этого достаточно для растягивания перебора, но недостаточно для того, чтобы
беречь платный ресурс: подряд пять запросов кода обошлись бы в 2+4+6+8+10 = 30 секунд
вместо прежних жёстких 60 между каждым. Заведён отдельный `throttle_otp_delay` (по
умолчанию 60, тот же порядок величины, что и старая константа), применяемый только к
scope `otp_send`. Жёсткого обрыва на N-й отправке при этом больше нет: решение 4 запрещает
`throttle_lockout` для ключа идентификатора при любом scope, а `otp_send` считается именно
по телефону как идентификатору. Растущая задержка без потолка признана достаточной заменой
осознанно — жёсткий обрыв для идентификатора это тот же рычаг DoS, что и для входа.

## Итог

| Вопрос постановки AUTH-49 | Ответ |
|---|---|
| По чему считать лимит | два независимых счётчика: идентификатор как введён, и IP |
| Где хранить | своя таблица агрегатных окон; не сессия, не `wa_login_log` |
| Что показывать | задержка → капча; жёсткая блокировка только по явному решению админа |
| Пересечение с `captcha_plugin` | режим `off`/`always`/`after_n` рядом с id плагина |
| Часть метода/контроллера или отдельный guard | ни то, ни другое: ядровой сервис перед резолвом контакта |
