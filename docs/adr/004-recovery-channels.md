# ADR 004. Восстановление пароля: `authRecoveryProvider`, а не встроенная email-форма

- **Статус:** принято
- **Дата:** 2026-09-18
- **Контекст задачи:** AUTH-48

## Контекст

До этой задачи восстановление — один email-путь, зашитый в
`authFrontendRecoveryAction`: форма принимает email, инлайн-SQL ищет контакт по
`wa_contact_emails`, `waMailMessage` шлёт ссылку с токеном, по токену ставится
новый пароль. Постановка AUTH-48 требует проработать сценарии, которые в эту
форму не ложатся: у контакта может не быть email (только телефон), может не
быть ни того ни другого, методов входа может быть несколько.

Обсуждение задачи добавило требование, которого не было в исходной
постановке: сторонний плагин может реализовывать вход по собственному
составному полю («email или телефон» одним инпутом, с паролем), и такой
плагин должен уметь сам понимать, что ему ввели, и сам восстанавливать доступ
своим пользователям — не полагаясь на то, что ядро угадает форму его
идентификатора. Это требование определяет форму решения целиком: восстановление
не может остаться сервисом ядра, который сам распознаёт email/телефон по regex
и лезет в `wa_contact_emails`/`wa_contact_data`, — иначе сторонний метод с
собственной моделью идентичности восстановление не получает никогда. Значит,
восстановление — такая же точка расширения, как `authMethod`/`authGuard`/
`authCaptcha`/`authThrottleStore`: узкий интерфейс, который реализует и ядро
(для встроенных `email`/`phone`), и любой плагин со своей логикой.

Разбор кода дополнительно вскрыл дефекты в исходной email-only реализации:
восстановление искало контакт без приведения регистра (`Bob@x.com` и
`bob@x.com` — два разных адреса для поиска, хотя весь остальной app
нормализует), шаг установки пароля не проверял длину, письмо не было
локализовано, а таблица токенов не имела уникального ключа по запросу —
повторные обращения копили живые токены.

## 1. Восстановление — плагинная точка расширения, по образцу `authThrottleStore`

Новый интерфейс `authRecoveryProvider`:

```php
interface authRecoveryProvider
{
    public function getId(): string;
    public function claims(string $identifier): bool;
    public function start(string $identifier): authRecoveryHandle;
    public function needsCode(): bool;
    public function verifyCode(authRecoveryHandle $handle, string $code): bool;
    public function complete(authRecoveryHandle $handle): ?int;
}
```

Плагин объявляет `is_recovery_provider => true` в `plugin.php`;
`authPluginManager::loadPlugin()` сверяет флаг↔интерфейс в одном блоке с
`is_throttle_store`/`is_captcha`. `recovery_channels` принимает и встроенные id
(`email`, `phone`), и id плагинов — тот же формат, что у
`login_methods`/`guard_plugins` (вплоть до именованных инстансов
`oidc_plugin:gitlab`).

Встроенные `authEmailRecoveryProvider`/`authPhoneRecoveryProvider`
реализуют интерфейс так же, как это делал бы сторонний плагин, и
регистрируются `authPluginManager::getRecoveryProvider()` по умолчанию под id
`email`/`phone` — никакого привилегированного пути внутри `authRecovery`,
который остаётся тонким координатором и не содержит слова "email" или
"phone" ни в одной строке кода.

Из этого следует ответ на исходный вопрос AUTH-48 («может быть несколько
методов входа, какой использовать для recovery») и на вопрос про составное
поле: провайдер и есть тот, кто понимает форму своего идентификатора. Ядру не
нужно знать про email/телефон вообще — оно знает только про интерфейс.

**Граница ответственности.** Провайдер владеет только связкой
«идентификатор → контакт» и доставкой доказательства; сам пароль
(`wa_contact.password`) провайдер никогда не трогает — его ставит ядро
(`authFrontendRecoveryAction`) после `complete()`, на `contact_id`, который
вернул провайдер. Без этой границы `authHelper::hasPasswordLogin()` (половина
шлюза доступности ниже — «есть ли что сбрасывать») теряет смысл: провайдер
мог бы устанавливать доступ к аккаунту, который никогда не был обусловлен
наличием пароля.

**Шлюз доступности** — свойство домена, не метода входа:

```
hasRecovery() = recovery_enabled
              && authHelper::hasPasswordLogin()            // есть что сбрасывать
              && authPluginManager::getRecoveryProviders()  не пуст
```

До этой задачи `HAS_RECOVERY` было константой конкретного метода входа, и
склеивало два независимых вопроса: «есть ли что сбрасывать» (это
`USES_PASSWORD`) и «есть ли канал доставки». Следствие: `authLoginMethod`
(логин+пароль) имел `HAS_RECOVERY = false`, и на домене только с ним страница
восстановления отдавала 404 — у человека с паролем и подтверждённым email не
было восстановления вовсе. `HAS_RECOVERY`/`has_recovery` убраны целиком:
константы у пяти встроенных методов входа, `authHelper::methodHasRecovery()`,
чтение флага из `getInfo()` (проверено — ни один плагин в `plugins/` его не
объявлял). Зеркально `uses_password` стал **несущим**: сторонний паролевый
метод входа, забывший этот флаг, теперь получит 404 на восстановлении своего
домена.

Ни одна часть шлюза не смотрит на контакт — оракула по построению нет.
Побочно: домен только с `authLoginMethod` теперь получает восстановление;
домен только с OAuth/телефонным OTP-входом (без включённого провайдера)
по-прежнему его не получает, потому что пароля там нет.

## 2. `recovery_channels` — явная доменная настройка, по умолчанию `['email']`

Не выводится из `login_methods`. SMS стоит денег и расширяет поверхность
(SIM swap даёт вход туда, куда домен по SMS не пускает) — включение
SMS-канала должно быть решением админа, а не следствием включённого
OTP-входа.

Порядок элементов — не косметика, а порядок проверки `claims()` (решение 3):
провайдер, перечисленный раньше встроенных, перехватывает формы, которые
иначе достались бы им. Экран бэкенда «Восстановление» хранит этот порядок как
порядок отображения чекбоксов — тот же принцип, что уже применён к
`login_methods` на экране «Вход»: список не переставляется мышью, порядок
задаётся тем, в каком порядке провайдеры перечислены в шаблоне
(встроенные — первыми, затем установленные плагины), а сохраняется он в том
порядке, в каком браузер отправил отмеченные чекбоксы — то есть в порядке
отображения.

## 3. Владелец идентификатора — провайдер, ядро не классифицирует централизованно

Форма — одно поле. Ядро (`authRecovery::request()`) перебирает провайдеров из
`recovery_channels` **в заданном порядке** и берёт первого, чей
`claims($identifier)` вернул true; ни один не подошёл → ошибка формата с
общим текстом («введите email или телефон»), не зависящая ни от одного
аккаунта — только от списка включённых провайдеров, то есть не оракул.

Этим вопрос «какой канал использовать, если методов входа несколько» снимается,
а не решается приоритетом по контакту: приоритет по контакту потребовал бы
сперва его найти, то есть построить оракул. Приоритет здесь — только порядок
проверки формы ввода, заданный админом в `recovery_channels`.

Плагин с составным полем «email или телефон» — ровно тот случай, ради
которого появился весь этот интерфейс: его `claims()` может вернуть true для
обеих форм сразу, внутри `start()` он сам решает, как резолвить контакт и
куда слать доказательство. Если такой плагин включён в `recovery_channels`
перед встроенными, он полностью подменяет их для форм, которые `claims()`
себе забирает.

## 4. `wa_contact.login` встроенными провайдерами не принимается

`authEmailRecoveryProvider`/`authPhoneRecoveryProvider` не заявляют `claims()`
на голый логин — он не адрес доставки, а имя аккаунта. Владелец
логин-аккаунта восстанавливается по своему email, если `email` включён в
`recovery_channels`. Сторонний провайдер волен принять и логин, если знает,
куда по нему написать (например, ведёт свою таблицу «логин → email») — это
его выбор и его ответственность за анти-перечисление, контракт интерфейса
это разрешает.

## 5. Ответ формы одинаков для всех исходов существования — требование контракта, не деталь реализации

Одна и та же отрисованная страница для: контакта нет; контакт есть и
сообщение ушло; отправка упала (`waSMS`/SMTP бросили). Подсказка «не
пришло — напишите в поддержку» показывается безусловно, всем.

Отдельного исхода «контакт есть, но каналов нет» не существует: по решению 3
идентификатор *и есть* адрес доставки, так что контакт без email и телефона
формой (для встроенных провайдеров) просто никогда не находится. Вопрос
постановки «чем заменить, ручная поддержка?» отвечается так: в теле ответа —
ничем (любой отдельный ответ для такого случая показывался бы только
существующим контактам), вне ответа — безусловная подсказка про поддержку.

Это требование контракта интерфейса (`start()`, `complete()`), а не деталь
одной телефонной ветки — с плагинами ядро физически не может проверить, что
провайдер его соблюдает; оно может только задать контракт и протестировать
встроенные реализации на соответствие ему (`authRecoveryTest`).

**Телефонная ветка ломает это требование, если делать её наивно, и это был
главный источник риска задачи.** Успех email-ветки и её промах выглядят
одинаково («письмо отправлено»), а у телефонной успех — это *форма ввода
кода*. Наивная реализация (`есть pending → форма кода; нет → страница
«отправлено»`) — искомый оракул, причём хуже email-ового: ответ бинарный,
мгновенный, на каждый введённый номер.

Поэтому встроенный `authPhoneRecoveryProvider::start()` **всегда** возвращает
хендл на ожидание кода, в том числе когда номер не разрезолвился, — заводя
строку-обманку (`contact_id = 0`, реальная строка в БД, а не счётчик в
сессии). Обманка получает настоящий `code_hash` — сгенерированный и
захешированный шестизначный код, который просто никуда не отправляется, а не
пустую строку: пустой `code_hash` увёл бы обманку в ветку «токен без кода»,
а не в общую с настоящим запросом. `verifyCode()` проваливает обманку
неотличимо от неверного кода: те же попытки, тот же TTL, то же сообщение,
то же уничтожение строки на пятой попытке.

**SMS не отправляется, но `otp_send`-throttle обязан посчитаться и отказывать
так же, как для настоящего номера — иначе оракул просто переезжает на уровень
ниже.** Счётчик один на нормализованный номер независимо от того, существует
ли контакт, поэтому и отказ после нескольких запросов подряд наступает на
одном и том же по счёту запросе что для настоящего номера, что для
придуманного — если бы отказ был виден только на настоящем (например, потому
что для обманки нет ни счётчика, ни повода его завести), это был бы тот же
класс различимости, что и на уровне ответа формы, просто на уровень ниже:
не форма ответа на один запрос, а поведение при повторных запросах на один и
тот же идентификатор.

Поэтому отказ **видим и одинаков** для обоих случаев, а не только сама
экономия SMS-бюджета: `authPhoneRecoveryProvider::start()` проверяет
`authThrottle::check('otp_send', …)` **до** резолва номера в контакт и, если
`$state->blocked`, бросает `authRecoveryThrottledException($state->retryAfter)`
— `authRecovery::request()` ловит её и рендерит тот же
`authThrottle::blockedMessage()`, что и для собственного IP-throttle сцены
`recovery`. Проверка до резолва — не только для симметрии ответа: она же не
даёт заблокированному запросу платить и за резолв контакта отдельным
таймингом. `hit('otp_send', …)` вызывается только когда `check()` не
заблокировал — иначе уже заблокированный номер продолжал бы копить попытки
сверху, расходясь с тем, что видит настоящий отправитель SMS. Любой сторонний
провайдер, метрирующий свой платный ресурс, обязан бросать то же исключение
на тех же условиях — это часть контракта `authRecoveryProvider::start()`, не
частность встроенного провайдера телефона.

## 6. Хранилище: общая таблица под любой провайдер, требующий код

`auth_password_recovery` получила форму `auth_profile_confirm`: `channel`
(id провайдера из `recovery_channels`, 64 символа — формат `login_methods`
допускает `myplugin_plugin`/`oidc_plugin:gitlab`, 16 символов не хватало),
`identifier_hash` (sha256 нормализованного идентификатора — по образцу
`auth_throttle.key_hash`, в сыром виде это чей-то email или телефон),
`code_hash`, `attempts`. `channel` говорит ядру, каким провайдером
обслуживать `verifyCode`/`complete` для этой строки — не потому что ядро
знает про email/телефон, а потому что оно знает, какой провайдер
зарегистрирован под этим id. Провайдер без кода (email) просто не заполняет
`code_hash`; токен в URL `recovery/<token>/` для такого провайдера и есть
доказательство. Провайдер с кодом (телефон, и любой сторонний с
`needsCode() === true`) держит хендл (channel + token) в
`wa()->getStorage()`, а не в URL — токен из URL для него не доказательство,
а дескриптор запроса, который к тому же никогда туда и не попадает.

**Уникальный ключ — `(identifier_hash, channel)`, не `(contact_id, channel)`.**
Это не косметика: по решению 5 все обманки телефонной ветки несут один и тот
же `contact_id = 0`. При ключе на `contact_id` вторая обманка (заведомо
несуществующий номер, отправленный из отдельной сессии) заменяла бы строку
первой обманки — и после такой перезаписи «неверный код» на настоящем
запросе и «код устарел» на чужой обманке перестали бы различаться только
случайно, ломая ровно то свойство, ради которого обманки вообще заводятся.
Ключ на хеше идентификатора убирает эту коллизию: разные телефоны — разные
хеши, обманки друг друга не задевают, а повторный запрос **того же**
идентификатора по-прежнему заменяет свою прежнюю строку (тот же довод, что в
докблоке `authProfileConfirmModel::issue()`: два живых токена на один
идентификатор означают, что старое письмо/код продолжает работать после
того, как визитёр исправил опечатку). Побочный эффект, отмеченный отдельно,
чтобы не читался как забытый случай: контакт с двумя recovery-годными
email-адресами может держать два живых токена одновременно, по одному на
каждое подтверждённое значение — это осознанно допустимо, а не дыра.

Попытки ввода кода считаются в колонке `attempts` строки (лимит 5,
`authPasswordRecoveryModel::MAX_ATTEMPTS`), а не в сессии — отличие от
решения 7 ADR 003, и оно осознанное: там довод был «лимит живёт не дольше
кода, сброс сессии обесценивает и код», а здесь код переживает сессию в БД
(письмо может быть открыто позже, код может вводиться после переоткрытия
вкладки), и сессионный счётчик обходился бы сбросом куки.

## 7. Throttle: оркеструет ядро, ресурсные лимиты — забота провайдера

| Что | Кто считает | scope | ключи |
|---|---|---|---|
| Сама форма (любой провайдер) | ядро, до выбора провайдера | `recovery` | IP (решение 4 ADR 003 — не по идентификатору) |
| Расход платного ресурса (SMS и т. п.) | сам провайдер, внутри `start()` | свой (у встроенного — `otp_send`) | провайдер сам решает |

`authThrottle` — публичный статический сервис, любой провайдер может звать
его сам. Ядро не придумывает для провайдеров общий «ресурсный» хук: разные
провайдеры тратят разные ресурсы (SMS, push, что угодно стороннее), и
решение 2 ADR 003 уже отвечает, что политика throttle не плагинизируется, а
вызов — да.

Встроенный `authPhoneRecoveryProvider::start()` считает `otp_send` по
нормализованному номеру — расход платного ресурса должен быть из одного
бюджета независимо от того, какая форма его запросила, иначе восстановление
стало бы обходом лимита `authPhoneMethod::sendOtp()`.

Шаг токена email-провайдера throttle не получает: 54 hex-символа
(`random_bytes(27)`) не подбираются.

## 8. Нормализация — внутри провайдера, не общая для всех каналов

Каждый провайдер нормализует свою форму идентификатора сам — ядро не может
знать, как нормализуется чужая форма (составное поле стороннего плагина,
например). Встроенные:

- email — `mb_strtolower(trim())` перед поиском (выравнивает восстановление с
  `authProfileSectionLoginEmail::normalize()` и чинит дефект из Context: до
  этой задачи `Bob@x.com` и `bob@x.com` были разными адресами для поиска);
- телефон — та же цепочка, что в `authProfileValues::preparePhones()`
  (`waContactPhoneField::cleanPhoneNumber()` поверх приватного `transformPhone()`,
  вынесенных в публичный `authProfileValues::normalizePhone()`), и она же
  идёт ключом в `otp_send`.

Это поправка к решению 3 ADR 003 («ключ — как введён, до резолва»):
формулировка имелась в виду как «до резолва в контакт», а не «без
нормализации»; без нормализации `+7 900…` и `8900…` были бы двумя счётчиками
на одного человека. Не читать как противоречие двух ADR — это уточнение
одной и той же мысли, а не пересмотр.

Вне этой задачи остаётся отдельная накладка: `authThrottle::normalize()` и
вызов `authPhoneMethod::sendOtp()` до сих пор кладут сырой номер без
нормализации, поэтому бюджеты `otp_send` восстановления и входа сольются
только после отдельного фикса — заведена задача, см. AGENTS.md/трекер.

## Приложение: границы, которые остались за скобками

- **CSRF на анонимных формах.** Проверено в ядре: куку `_csrf` ставит только
  `waAuthUser` (`wa-system/user/waAuthUser.class.php`) и только для
  залогиненного посетителя. У анонима куки нет, поэтому `{$wa->csrf()}` в
  `recovery.html` печатает пустое значение, а штатная сверка
  `waRequest::post('_csrf') != waRequest::cookie('_csrf')` вырождается в
  `'' == ''` и пропускает всё. Добавлять сверку в
  `authFrontendRecoveryAction` бессмысленно: она не сломает восстановление,
  но и не защитит. Настоящая защита анонимных форм требует собственного
  токена, выдаваемого на GET, и нужна `login.html`/`register.html`/
  `recovery.html` одинаково — отдельная задача, не входит в AUTH-48.
- **Оракул на форме входа (не восстановления).** `authPhoneMethod::sendOtp()`
  бросает «Пользователь с таким номером не найден.» — это перечисление на
  форме **входа**; email-ветка входа там намеренно молчит. Обнаружено при
  разборе кода, к восстановлению отношения не имеет — отдельная задача.

## Итог

| Вопрос постановки AUTH-48 | Ответ |
|---|---|
| У контакта нет email, только телефон | `recovery_channels` может включать `phone`; телефонный провайдер шлёт код, а не ссылку |
| У контакта нет ни email, ни телефона | Идентификатор без claims-совпадения получает ту же ошибку формата, что и мусор — контакт при этом не резолвится вовсе, оракула нет |
| Несколько методов входа одновременно — какой использовать | Канал определяется формой введённого идентификатора (`claims()`), а не привязкой к конкретному методу входа |
| Заложить в `authFrontendRecoveryAction`/`has_recovery` до реализации | Оба переписаны: `hasRecovery()` — домена, не метода; `authFrontendRecoveryAction` — тонкий фасад над `authRecovery` |
| (сессия) Плагин с составным email/phone-полем должен сам восстанавливать доступ | `authRecoveryProvider` — новая точка расширения; плагин владеет классификацией, резолвом и доставкой целиком |
