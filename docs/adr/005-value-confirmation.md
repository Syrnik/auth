# ADR 005. Подтверждение email/телефона: второстепенные значения, штампы статуса, строгий вход

- **Статус:** принято
- **Дата:** 2026-09-19
- **Контекст задачи:** AUTH-51

## Контекст

Постановка AUTH-51 утверждала, что во фреймворке нет штатного места для факта «телефон
подтверждён» — это неверно. Место есть и используется остальным фреймворком:
`wa_contact_emails.status` (enum, `waContactEmailsModel::STATUS_CONFIRMED = 'confirmed'`) и
`wa_contact_data.status` (varchar, `waContactDataModel::STATUS_CONFIRMED = 'confirmed'`,
`STATUS_UNKNOWN = NULL` — не совпадает по типу с email-версией, `'unknown'`). Готовые писатели —
`waContactEmailsModel::updateContactEmailStatus()` и `waContactDataModel::updateContactPhoneStatus()`
— уже делают то, что нужно: не трогают статус, если он уже совпадает, возвращают `false`, если
значения нет на контакте. Фреймворк штампует `confirmed` в трёх местах
(`waSignup.action.php:227`, `waBaseLogin.action.php:271`, `waBaseForgotPassword.action.php:248/259`)
— у `auth` работающих аналогов не было ни одного.

Задача была расширена в двух направлениях по итогам обсуждения с владельцем: (1) подтверждения
требует не только логинное значение (`sort = 0`), но и второстепенные email/телефоны; (2) вход
может строго блокироваться, если логинный email не подтверждён.

## 1. Второстепенные значения тоже подтверждаются — не withholding, а stamp-after-save

**Решение.** Второстепенный email/телефон сохраняется сразу, как и раньше (`getConfirmationUrl()`
для `authProfileSectionEmail`/`Phone` теперь всегда возвращает `null`). Подтверждение — отдельное
действие «Подтвердить» (`my/confirm/send/<section>/`, `authFrontendMyConfirmSendController`),
запускаемое посетителем когда удобно; результат — только штамп `status = confirmed`, значение уже
на контакте.

**Это отменяет последний пункт решения 2 ADR 001**, который гласил:

> Значения дальше по списку — обычные поля контакта и подтверждения не требуют.

Начиная с этой задачи это неверно: второстепенное значение подтверждения требует, только не тем
же способом, что логинное (изъятие до доказательства). Решение 2 ADR 001 не переписывается задним
числом — оно фиксировало корректное на тот момент разделение «логин против поля контакта»; эта
запись фиксирует, что подтверждаемость — не то же самое, что «является логином».

**Почему не withholding.** У второстепенного значения нет риска потери доступа при опечатке — оно
не единственный способ входа. Требовать доказательства до сохранения означало бы городить второй
`auth_profile_confirm`-подобный механизм ради значения, которое и так безопасно хранить
неподтверждённым.

**Как это устроено в коде.** Общая инфраструктура вынесена в трейты
(`lib/classes/profile/authProfileConfirmableValue.trait.php`,
`authProfileConfirmEmail.trait.php`, `authProfileConfirmPhone.trait.php`), которые используют и
`authProfileSectionLogin`/`LoginEmail`/`LoginPhone` (изъятие нового значения), и
`authProfileSectionEmail`/`Phone` (подтверждение уже сохранённого) — issue/send/rollback ровно
один, разница только в том, когда он вызывается и что происходит с полем после. Интерфейс
`authProfileSectionConfirmable` расширен методами `sendConfirmation(?int $index)` и
`isConfirmed(?int $index)` — оба объявлены прямо в интерфейсе (не только в трейте), потому что
`my/confirm/send/` типизирует секцию именно через `authProfileSectionConfirmable`, а на момент
принятия решения ни один сторонний плагин этот интерфейс не реализовывал — расширение не ломает
существующих реализаций.

**Секция логина тоже получила эту возможность для своих значений с индексом > 0.**
`authProfileSectionLoginEmail`/`Phone` показывают полный список (логин на `sort = 0` плюс все
второстепенные того же поля), и `sendConfirmation($index)` для `$index > 0` работает так же, как
у обычной секции. `applyConfirmedValue()` больше не получает индекс — интерфейс
`authProfileSectionConfirmable::applyConfirmedValue(string $value): bool` этого не менял, чтобы не
трогать точку расширения — поэтому различение «это новый логин (писать в `sort = 0`) или
переподтверждение уже сохранённого значения (только штамп)» сделано через
`isAlreadyStored()`: если `$value` уже есть где-то в списке секции, это переподтверждение;
`getConfirmationUrl()` гарантирует, что значение, для которого он выпустил строку, в списке
отсутствовало на момент выпуска.

## 2. Колонка `section` в `auth_profile_confirm` — против подмены секции при погашении токена

**Проблема, найденная при проектировании.** `auth_profile_confirm` хранит `(contact_id, field,
value, token)`, но не то, какая секция выпустила строку. До этой задачи `authFrontendMyConfirmAction
::apply()` резолвил секцию через `authProfileSectionRegistry::getConfirmable($row['field'])` **в
момент погашения токена**, а не в момент выпуска. Раз второстепенные значения теперь тоже выпускают
строки под тем же `field`, что и логинная секция, — домен, поменявший `login_methods` за то время,
что токен ещё жив (TTL 1 час), мог получить строку, выпущенную обычной секцией `email`, погашенную
через `authProfileSectionLoginEmail`, чей `applyConfirmedValue()` пишет значение на `sort = 0` —
второстепенный адрес превращается в логин, минуя `isTaken()` и вообще весь смысл решения 2 ADR 001.

**Решение.** `auth_profile_confirm` получила колонку `section` (varchar, default `''`),
записываемую `issue()` (пятый параметр, `$this->getId()` со стороны вызывающей секции).
`authFrontendMyConfirmAction::resolveSection()` резолвит **только** названную секцию
(`authProfileSectionRegistry::getSection($row['section'], ...)`, с проверкой
`instanceof authProfileSectionConfirmable`) — и если она сейчас недоступна (конфиг поменялся),
возвращает `null`, а не откатывается на резолюцию по `field`. Откат на `getConfirmable($field)`
происходит только для строк с пустой `section` — то есть только для строк, выпущенных до этой
миграции; после неё других причин для пустого значения нет.

**Почему без отката на "похожую" секцию, а не просто безопаснее.** Разрешить fallback на
`getConfirmable($field)`, когда именованная секция недоступна, воссоздало бы исходную уязвимость
ровно в том случае, для которого колонка вводилась, — единственный корректный ответ на «секция,
которая это выпустила, больше недоступна» — отказ применения (`showPage(null, 'This change can no
longer be applied.')`), не догадка.

## 3. Одна ожидающая заявка на поле — уникальный ключ не расширяется

**Решение.** `(contact_id, field)` остаётся уникальным ключом `auth_profile_confirm`. Запрос
подтверждения одного второстепенного значения тихо снимает более раннюю заявку по тому же полю
(документировано в `authProfileConfirmModel::issue()` с самого начала).

**Компромисс.** У контакта с двумя неподтверждёнными второстепенными email при запросе
подтверждения второго адреса заявка по первому (уже отправленное письмо) молча перестаёт работать.
Расширение ключа до `(contact_id, field, value)` позволило бы независимые параллельные
подтверждения, но: (а) даёт визитёру возможность держать N живых токенов и тратить N SMS-бюджетов
одновременно по одному полю; (б) требует правки `getPending(contact_id, field)` (стал бы
неоднозначным без `value`), `getWaitUrl(string $field)` и вручную собранных ссылок в
`my.profile.login_email.view.html`/`login_phone.view.html`. Решено не делать этого ради AUTH-51 —
это не тот объём, который оправдан этой задачей.

## 4. Строгий вход: `authLoginConfirmGate`

**Решение.** Новая настройка домена `login_require_confirmed` (по умолчанию `false`). Вход
блокируется, только если:

```php
login_require_confirmed && signup_confirm && in_array('email', signup_fields, true)
```

— все три условия читаются в одном месте, `authLoginConfirmGate::isEnabled()`, при каждом вызове,
а не сверяются друг с другом на бэкенде в момент сохранения. Причина: `signup_confirm` и
`login_require_confirmed` редактируются на **разных** экранах бэкенда (Регистрация и Вход
соответственно); проверка «на сохранении» одного экрана не видит состояние другого, и админ может
включить строгий вход, затем выключить `signup_confirm` на другом экране, не заметив, что первое
только что осиротело. Чтение обоих условий вживую при каждой проверке устраняет саму
возможность рассинхронизации.

**Почему именно `signup_confirm` и `signup_fields`, а не просто флаг.** Если `signup_confirm`
выключен, `authFrontendRegisterAction` авторизует новый контакт напрямую
(`wa()->getAuth()->auth(...)`), минуя `authenticate()` вовсе — то есть аккаунт, созданный в этом
режиме, никогда не проходил через `authenticate()`, а значит гейт применится только к его
**следующему** входу, у аккаунта, которому ничего не предлагали подтвердить. Гейтинг на
`signup_confirm` делает «просим доказательство при регистрации» и «требуем его при входе» одним
решением, которое нельзя рассинхронизировать.

## 5. Отказ гейта — `authGuardException`, никогда не `authCredentialFailureException`

**Решение.** `authLoginUnconfirmedException extends authGuardException` (не
`authCredentialFailureException`). Пароль был введён верно — это не ошибка учётных данных, и
throttle не должен её засчитывать (решение 1 `docs/adr/003-credential-throttle.md`:
`authCredentialFailureException` существует специально для настоящего несовпадения пароля/логина).
Легитимный владелец аккаунта, созданного до включения этой настройки, не должен тратить свой
throttle-бюджет на состояние, которое целиком — решение домена, а не что-то, что он сделал не так.

## 6. Какие методы исключены из гейта, и почему

`authLoginConfirmGate::fieldFor(authMethod $method): ?string` возвращает `'email'` только для
`authEmailMethod`. Остальные исключены конструктивно:

- **`authPhoneMethod`** — успешный OTP-вход и есть доказательство: `authPhoneMethod::verifyOtp()`
  штампует `confirmed` в том же запросе. Гейт, проверяющий подтверждённость ДО входа, не должен
  мешать именно тому входу, который её устанавливает.
- **`authLoginMethod`** (вход по `wa_contact.login`) — для этого поля во фреймворке вообще нет
  хранилища статуса подтверждения. Проверять нечего.
- **OAuth/плагинные методы** — провайдер ручается за личность своим механизмом, который это
  приложение не моделирует как «подтверждено/не подтверждено» вовсе (см. комментарий
  `authWaidAdapter` про доверие подтверждённым email провайдера).

`fieldFor()` намеренно не стал методом интерфейса `authMethod` — этот интерфейс точка расширения
для плагинов, и обязательный новый метод сломал бы каждую стороннюю реализацию ради проверки,
нужной только одному встроенному методу.

## 7. Пять точек, где приложение теперь пишет `status = confirmed`

Ни одна не писала его раньше:

1. Подтверждение смены логина в профиле — `authProfileSectionLogin::applyConfirmedValue()`, после
   успешного `parent::save()` (не до — `authProfileValues::preparePhones()` прочитал бы значение
   как ещё не сохранённое и записал бы его неподтверждённым).
2. Подтверждение регистрации — `authFrontendConfirmAction`, штампует адрес, на который письмо было
   реально отправлено (`auth_signup_confirm.email`), а не текущий `sort = 0` на момент клика —
   визитёр мог сменить адрес между регистрацией и переходом по ссылке.
3. Успешный OTP-вход по телефону — `authPhoneMethod::verifyOtp()`.
4. Завершённое восстановление пароля (оба канала) — `authFrontendRecoveryAction::finishRecovery()`,
   через `authContactStatus::confirmPrimary($channel, $contact_id)`. Плейнтекст идентификатора не
   тащится через `authRecoveryProvider` (точка расширения для плагинов, ADR 004) — оба встроенных
   провайдера резолвят строго по `sort = 0`, так что восстановленный идентификатор и есть логин.
   `confirmPrimary()` молча не делает ничего для канала, не являющегося `'email'`/`'phone'`
   (плагинный канал восстановления) — специальной обработки не требуется.
5. Явное действие «Подтвердить» для уже сохранённого второстепенного значения —
   `authFrontendMyConfirmSendController` → `sendConfirmation()` → (после погашения токена)
   `applyConfirmedValue()`.

Общая точка записи — `authContactStatus` (`lib/classes/authContactStatus.class.php`): единственное
место, которое знает про асимметрию `STATUS_UNKNOWN` (`waContactEmailsModel` — строка `'unknown'`,
`waContactDataModel` — `NULL`) и про то, что `updateContactPhoneStatus()` требует значение,
нормализованное так же, как `authProfileValues::preparePhones()` его хранит (`cleanPhoneNumber()`
поверх `transformPhone()`, не просто `cleanPhoneNumber()`).

## 8. Throttle на подтверждение — общий scope `otp_send`, без пересечения бюджетов

`authProfileConfirmableValueTrait::startConfirmation()` — общая точка для обоих вызывающих
(`authProfileSectionLogin::getConfirmationUrl()` и `sendConfirmation()`) — троттлится по scope
`otp_send`, тому же, что уже используют `authPhoneMethod` и `authPhoneRecoveryProvider` для SMS.
До этого метода `getConfirmationUrl()` смены логина вообще не был ограничен — расшаривание одной
реализации закрывает этот пробел заодно с новым эндпоинтом, а не только для него.

Email- и SMS-подтверждения не делят один бюджет, несмотря на общий scope: ключ `authThrottle` —
хэш самого значения (`['login' => $value]`), а email и телефон — разные строки, значит разные
хэши, значит разные окна независимо от scope.

## 9. Автоматического backfill нет

`login_require_confirmed` по умолчанию выключена — обновление приложения никого не блокирует.
Задним числом помечать существующие аккаунты подтверждёнными в апдейтере не стали: «есть пароль и
давняя история входов» — не доказательство, что адрес когда-либо был доступен, а именно это
предположение задача и существует, чтобы перестать делать. Батч-`UPDATE` по всей
`wa_contact_emails` в апдейтере — риск на деплое сам по себе.

Для администратора, который сознательно принимает это допущение, — SQL, не выполняемый
автоматически:

```sql
UPDATE wa_contact_emails e JOIN wa_contact c ON c.id = e.contact_id
   SET e.status = 'confirmed'
 WHERE e.sort = 0 AND c.password != '' AND c.is_user > -1
   AND (e.status IS NULL OR e.status <> 'confirmed');
```
