# ADR 006. Удаление плагина целиком: чистка конфига и данных контактов

- **Статус:** принято
- **Дата:** 2026-09-28
- **Контекст задачи:** AUTH-559, продолжение AUTH-440 (ADR 002)

## Контекст

Удаление плагина на экране «Плагины» выполняет не `authPluginsActions` (тонкая обёртка
над `waPluginsActions`, она удалением не занимается), а инсталлер: кнопка ведёт на
`installer/?module=plugins&action=remove`, где `installerPluginsRemoveAction::removeExtras()`
последовательно:

1. вызывает `waSystem::getInstance('auth')->getPlugin($id)->uninstall()`;
2. удаляет запись из `wa-config/apps/auth/plugins.php`;
3. удаляет каталог `plugins/<id>/` и кеши.

Событий инсталлер не генерирует никаких: есть только `plugin.enable` и
`end_installation`, а `item_uninstall` — это запись в лог действий, не хук. Сам
`waPlugin::uninstall()` удаляет таблицы из `db.php` плагина, его `wa_app_settings` и
права, но ничего не знает о доменном конфиге auth (`wa-config/apps/auth/config.php`) и
о строках плагина в `wa_contact_data`.

В итоге после удаления в конфиге оставались `plugin_settings[<id>]` и id плагина в
доменных списках, а у контактов — привязки под его `getLinkSource()`. При повторной
установке плагина с тем же id он молча получал всё это обратно. Это та же уязвимость,
что закрыта в ADR 002 для удалённого *инстанса*.

## 1. Удаление плагина — то же событие, что удаление инстанса: чистим всё

**Решение.** `authPlugin::uninstall()` переопределён: перед `parent::uninstall()` он
вызывает `authPluginUninstaller::run()`. Тот:

- проходит **все** домены из сохранённого конфига, а не только те, где приложение
  сейчас смонтировано: запись на размонтированном домене тоже вернулась бы при
  переустановке;
- убирает `plugin_settings[<id>]` и все ссылки на плагин (любой его инстанс) из
  `login_methods`, `signup_methods`, `challenge_methods`, `recovery_channels`,
  `guard_plugins`; `captcha_plugin`/`throttle_store`, указывающие на плагин,
  становятся `null`;
- вызывает `purgeInstanceData()` для каждого инстанса multi-instance плагина (ключи
  собираются объединением `plugin_settings[<id>]` и `<id>_plugin:<key>` из всех списков
  по всем доменам), а для обычного плагина — для самого объекта плагина.

Порядок тот же, что на экране «Вход»: сначала запись конфига, потом данные.

`uninstall()` вызывается только на путях удаления: плагина (`installerPluginsRemoveAction`)
и приложения целиком (`installerAppsRemoveAction` вызывает `uninstall()` у каждого его
плагина). Обновление и переустановка поверх его не вызывают. Значит, при удалении
приложения auth привязки и 2FA-enrollment всех его плагинов тоже стираются — это
намеренно и согласуется с решением.

**Почему не только предупреждение.** Предупреждение ничего не меняет в исходе:
данные остаются, и переустановка их унаследует. Фреймворк сам при `uninstall()`
безусловно удаляет таблицы и настройки плагина, так что «удаление уносит данные» —
уже принятый контракт платформы; auth просто распространяет его на своё хранилище.

**Почему без исключения «настроено на другом домене» (ADR 002, решение 3).** Там
инстанс удалялся на одном домене и мог продолжать жить на другом. Здесь плагина не
остаётся нигде — сохранять привязки не для кого.

## 2. Сопоставление id: строгие и нестрогие списки

`login_methods`, `signup_methods`, `challenge_methods`, `recovery_channels` читаются
как `<id>_plugin[:<key>]`; голый id в них — встроенный метод (`email`, `phone`), и
плагин с таким же именем каталога его не трогает. `guard_plugins`, `captcha_plugin`,
`throttle_store` читаются нестрого (`authPluginManager` отрезает `_plugin`, только если
он есть), и экран «Защита» хранит в них именно голый id — там совпадает и то, и другое.
Префиксы не сравниваются: удаление `foo` не задевает `foobar_plugin`.

## 3. id плагина — из `getInfo()['id']`, не из `getId()`

`authMethod`/`authChallenge`/`authRecoveryProvider` переопределяют `getId()` как id
*метода*, который плагин выбирает сам. Имя каталога надёжно лежит только в
`$info['id']` — его ставят и `waSystem::getPlugin()`, и `authPluginManager::readPluginInfo()`.

## 4. Сбой чистки не блокирует удаление

Исключение из `authPluginUninstaller::run()` пишется в `auth/auth.log`, а
`parent::uninstall()` вызывается в любом случае. Застрявший на полпути инсталлер хуже
осиротевших данных, которые видно в логе.

## 5. TOTP теперь переопределяет `countInstanceContacts()`/`purgeInstanceData()`

ADR 002, решение 4, фиксировал, что `totp` ничего не переопределяет, потому что хук
для него не вызывается. С этой задачи вызывается — при удалении плагина. Enrollment
TOTP (`totp_secret`, `totp_last_step`) лежит не под `getLinkSource()`, поэтому
дефолтная реализация оставила бы секреты. `authTotpPlugin` переопределяет оба метода
и удаляет оба поля у всех контактов. После переустановки пользователи настраивают 2FA
заново — старые секреты из приложений-аутентификаторов больше не принимаются.

## Известные ограничения

- Если класс плагина не загружается, `getPlugin()` бросает исключение, и инсталлер
  переходит на `installerDummyPlugin::uninstall(true)`. Наш `uninstall()` в этом случае
  не вызывается, чистки не будет. Других точек входа у фреймворка нет.
- Привязки инстанса, который уже не упоминается ни в одном конфиге (удалён до AUTH-440),
  найти нельзя: его `source` не из чего вывести.

## Итог (дополняет таблицу ADR 002)

| Событие | Доменный конфиг | Привязки/enrollment |
|---|---|---|
| Плагин выключен в `plugins.php` | остаётся | остаются |
| Плагин удалён через инсталлер | чистится на всех доменах | стираются для всех инстансов |
| Плагин удалён, но класс не загрузился | остаётся (ограничение) | остаются |
